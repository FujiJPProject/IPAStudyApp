# Phase 3：アーキテクチャ設計

添付されている `requirements.md` と `ui-reference.html` をもとに、これから実装するWebアプリのアーキテクチャを設計してください。

今回は設計のみです。

実装、コード生成、ファイル作成はまだ行わないでください。

# Source of Truth

以下の優先順位で扱ってください。

1. `requirements.md`
   - 機能要件
   - MVP範囲
   - 画面・機能の責務
   - 学習体験
   - 非機能要件

2. `ui-reference.html`
   - 画面構成
   - 情報配置
   - UI上の操作感
   - レスポンシブ表示
   - 学習体験の見せ方

`ui-reference.html` はUI確認用プロトタイプです。

HTML / CSS / JavaScriptの内部構造を、そのまま本番実装の設計として採用しないでください。

特に、プロトタイプ内で以下が1ファイルに実装されていても、本番アプリでは適切に責務を分離してください。

・画面切り替え
・教材情報
・教材固有ロジック
・状態管理
・学習履歴保存
・UI描画

`requirements.md` と `ui-reference.html` に矛盾がある場合は `requirements.md` を優先してください。

ただし、重大な矛盾や設計判断に影響する不明点がある場合は、勝手に補完せず確認事項として提示してください。

# 技術上の前提

本番アプリは以下を基本技術とします。

・Vue 3
・TypeScript
・Vite
・Vue Router
・CSS
・Vitest

Vue 3ではComposition APIを基本としてください。

Single File Components（`.vue`）を前提として構いません。

# 設計条件

以下を満たすアーキテクチャを設計してください。

・ローカル開発可能

・Cloudflare Pagesへ静的デプロイ可能

・PCとスマートフォンの両方に対応可能

・Vue 3のComposition APIを基本とする

・MVPではバックエンドを持たない

・MVPでは認証を持たない

・MVPではサーバー側DBを持たない

・学習履歴はブラウザ・端末内に保存する

・UIとビジネスロジックを分離する

・UIから直接localStorage等の永続化処理を行わない

・教材情報と教材固有ロジックを分離する

・アプリ共通機能と教材固有機能を分離する

・ソート教材固有の処理をアプリ共通部分へ持たせない

・2つ目以降の教材を既存教材への大きな変更なしで追加できる

・将来的にDBや認証を追加しても教材固有ロジックを大幅に変更しなくてよい

・必要以上の抽象化や汎用フレームワークを作らない

・MVPで不要な将来機能を先回りして実装する設計にしない

# MVPで扱う機能

requirements.mdに従い、MVPでは以下を扱います。

## アプリ共通

・HOME

・学習一覧

・学習履歴

・ナビゲーション

・教材情報の管理

・教材を表示するための共通的な仕組み

## 教材

MVPでは、

・ソートアルゴリズム可視化

の1教材のみを実装対象とします。

ただし、ソートは代表教材の1つであり、アプリ全体をソート専用に設計しないでください。

将来的に、

・数学
・データベース
・ネットワーク
・セキュリティ
・その他アルゴリズム

など、異なる状態・処理・可視化方法を持つ教材を追加できることを前提としてください。

# 教材設計について

各教材は原則として自身の、

・初期状態・条件

・処理ロジック

・ステップ状態

・状態変化

・可視化UI

・教材固有の説明

を担当する構成を検討してください。

一方、アプリ共通部分は、

・ソートの比較処理

・交換処理

・配列

など、特定教材の内部仕様を知らなくてもよい構成を目指してください。

ただし、すべての教材を同じインターフェースへ無理に押し込むなど、MVP段階での過剰な抽象化は避けてください。

「2つ目の教材を追加しやすい最低限の境界」を設計してください。

# ルーティング方針

以下の画面をVue Routerで扱う前提で検討してください。

・HOME

・学習一覧

・可視化教材

・学習履歴

教材画面については、将来的な教材追加を考慮し、

例：

`/materials/:materialId`

のようなルーティングが適切か検討してください。

Cloudflare Pagesへの静的デプロイも考慮し、History Mode / Hash Modeのどちらを採用するか、その理由も示してください。

# 状態管理方針

状態を以下の種類に分けて検討してください。

## 画面ローカル状態

例：

・現在のステップ

・処理開始状態

・教材内での一時的な表示状態

## アプリ共通状態

例：

・教材情報

・必要であれば共通UI状態

## 永続化する状態

MVPでは、

・教材ID
・教材を最後に開いた日時

のみです。

Pinia等のグローバル状態管理ライブラリは、必要性が明確な場合のみ採用してください。

Vueの `ref`、`reactive`、`computed`、Composable等で十分な場合は、Piniaを導入しない選択を優先してください。

採用する場合も、なぜ必要なのか説明してください。

# 永続化方針

MVPでは学習履歴のみブラウザ・端末内へ保存します。

UIコンポーネントから直接 `localStorage` を操作する構成にはしないでください。

例えば、

```text
UI
↓
Composable / Service
↓
Repository
↓
localStorage
```

のような責務分離が適切か検討してください。

ただし、MVPとして層を増やしすぎないようにしてください。

将来的に、

```text
localStorage
↓
API / Supabase等
```

へ変更する場合に、UIや教材固有ロジックへの影響を抑えられる構成を目指してください。

# Composableの方針

Composition APIを利用するため、Composableとして切り出すべき責務があるか検討してください。

例えば、

・学習履歴の読み書き

・教材情報取得

・教材画面共通処理

などです。

ただし、単にコードを分割するためだけのComposableは作らない方針としてください。

# ソート教材について

ソート教材はMVPの代表教材ですが、現時点ではソート教材固有の詳細設計をアプリ全体のアーキテクチャへ持ち込まないでください。

`ui-reference.html` に存在する、

・固定配列

・バー表示

・比較状態

・交換状態

・ステップ数

・具体的なソート処理

などは、MVP教材を動作確認するための具体例です。

アプリ共通アーキテクチャがこれらへ依存しないようにしてください。

ソート教材内部の具体的なアルゴリズム設計については、後続の個別教材設計・実装フェーズで扱います。

# テスト方針

MVPとして必要十分なテスト方針を設計してください。

少なくとも以下について検討してください。

・教材固有ロジックの単体テスト

・学習履歴保存処理の単体テスト

・主要Composable / Serviceのテスト

・主要Vueコンポーネントのテスト

・主要画面遷移の確認

ただし、MVP段階で過剰なE2Eテスト環境や複雑なテスト基盤を導入しないでください。

どこをVitestで自動テストし、どこを手動確認するのか整理してください。

・ソート固有ロジックが共通部分へ漏れていないか

・機能間の依存が強すぎないか

・2つ目以降の教材を追加しやすいか
