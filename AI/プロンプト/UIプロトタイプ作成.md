# Phase 2：UIプロトタイプ作成

```md
添付されている `requirements.md` をもとに、UI確認用のプロトタイプを作成してください。

`requirements.md` を本プロトタイプのSource of Truthとして扱ってください。

今回は本番実装ではありません。

画面構成、情報設計、操作性、学習体験、レスポンシブ表示の妥当性を確認するためのプロトタイプを作成してください。

# 目的

以下を確認することを目的とします。

- 必要な画面が適切に構成されているか
- 各画面に必要な情報が過不足なく配置されているか
- ユーザーが迷わず学習を開始できるか
- 「初期状態 → 処理開始 → ステップ実行 → 状態変化 → 最終結果 → 解説」という学習体験がUI上で理解できるか
- HOME、学習一覧、可視化教材、学習履歴の画面遷移が分かりやすいか
- PCとスマートフォンの両方で操作しやすいか
- 将来的に教材が増えても利用できそうなUI構成になっているか

# 実装形式

- HTML / CSS / JavaScriptを1ファイルにまとめてください。
- ブラウザでHTMLファイルを直接開いて確認できる状態にしてください。
- Vue、React等のフレームワークは使用しないでください。
- バックエンドとの通信は行わず、必要な情報はダミーデータまたはJavaScript内のデータとして保持してください。

# 要件

添付されている `requirements.md` の内容に従ってください。

特に以下をMVPの前提としてください。

## 画面

以下の4画面を確認できるようにしてください。

1. HOME画面
2. 学習一覧画面
3. 可視化教材画面
4. 学習履歴画面

実際に別HTMLへ遷移する必要はありません。

1つのHTML内で画面切り替えを行い、画面遷移と操作感を確認できればよいです。

## HOME画面

以下を確認できるUIにしてください。

- アプリの目的
- このアプリでどのように学習するのか
- 学習を開始するための導線
- 学習一覧への導線
- 学習履歴への導線

## 学習一覧画面

MVPでは以下の教材1件のみ表示してください。

・ソートアルゴリズム可視化

教材について、

- 教材名
- 分野
- 概要

が確認できるようにしてください。

MVPでは教材は1件ですが、将来的に教材数が増えた場合にも一覧として成立するUIを意識してください。

ただし、存在しない教材を大量にダミー表示する必要はありません。

## 可視化教材画面

本アプリの中心となる画面です。

以下の学習体験をUI上で確認できるようにしてください。

概要
↓
初期状態・条件
↓
処理開始
↓
1ステップ実行
↓
現在の処理内容
↓
状態変化の可視化
↓
次のステップ
↓
最終結果
↓
なぜそうなるのか
↓
そこから何が分かるか

ソート教材については、配列やバー等を使い、比較対象や状態変化が視覚的に分かる簡易的な表現を使用して構いません。

ただし、今回の目的はソートアルゴリズム自体の詳細設計ではありません。

以下については作り込みすぎないでください。

- 具体的なソートアルゴリズムの選択機能
- 高度なアニメーション
- 速度変更
- 自由な配列入力
- 複雑な実行制御
- アルゴリズム固有の詳細設定

「1ステップ実行によって状態が変化し、その意味を確認できる」という学習体験を確認できれば十分です。

## 学習履歴画面

以下を確認できるUIにしてください。

- 過去に開いた教材
- 教材名
- 最後に開いた日時
- 履歴から教材を再度開く操作

MVPでは保存対象は、

- 教材ID
- 教材を最後に開いた日時

のみです。

学習時間、正答率、進捗率、理解度、スコア等は表示しないでください。

# 基本操作

最低限、以下を実際に操作できるようにしてください。

- HOME → 学習一覧
- HOME → 学習履歴
- 学習一覧 → 可視化教材
- 学習履歴 → 可視化教材
- 可視化教材で処理開始
- 可視化教材で1ステップ実行
- 複数回ステップ実行して状態が変化する
- 最終状態まで進める
- 主要画面から適切に戻る、または別画面へ移動する

# レスポンシブ対応

PCとスマートフォンの両方を想定してください。

特にスマートフォンでは以下を確認してください。

- 横スクロールが発生しない
- 主要操作ボタンを押しやすい
- 可視化部分が小さくなりすぎない
- 文章と可視化部分の関係が分かりやすい
- ナビゲーションが破綻しない
- 320px程度の画面幅でも主要機能を利用できる

PCでは画面幅を有効活用し、可視化部分と説明部分を適切に配置してください。

# デザイン方針

試験学習用Webアプリとして、

- 情報を読み取りやすい
- 操作対象が分かりやすい
- 現在何を確認しているのか分かる
- 装飾より学習内容を優先する

UIにしてください。

過度に派手な装飾やアニメーションは不要です。

# 制約

- バックエンド不要
- DB不要
- 認証不要
- ログイン画面を作らない
- ダミーデータでよい
- 自由な値入力機能は不要
- 複数教材を実装しない
- 問題演習機能を追加しない
- 学習分析機能を追加しない
- 本番用のVueコンポーネント設計を行わない
- 本番用のディレクトリ構成を決定しない
- 要件に存在しない将来機能を先回りして実装しない
- ソート専用アプリのようなUI構造にしない

# 要件との整合性

`requirements.md` に記載されている要件と、このプロンプトの指示が矛盾する場合は `requirements.md` を優先してください。

不明確な箇所について、UI確認のために軽微な仮定が必要な場合は、過剰な機能追加をせず最小限の仮定で表現してください。

要件自体の変更が必要だと判断した場合は、勝手に変更せず、プロトタイプ作成後に確認事項として報告してください。
```
